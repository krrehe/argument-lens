# 理论透镜：让同一段文本被六套理论分别检查

> 这份文档回答一个问题：为什么这个软件不提供「分析」，而提供「六种分析」，以及这六种分析在代码里是怎么分开的。

---

## 一、为什么必须分透镜

三件事凑在一起，只允许一种做法。

**第一，学科内部没有公认定义。** SEP《Fallacies》把教科书通说「看似有效而实际无效」拆成三个必要条件，然后写：*All three conditions have been brought into question*。无效性条件被 Massey 的不对称论题打掉，外观条件被 Johnson 用「频率」替换，论证条件被乞题与复杂问句反例打掉。定义不成立，判定就没有唯一出口。

**第二，分类学至少五套且互不兼容。** IEP 231 条自承 *The taxonomy of the fallacies is in dispute*；同一条违规有六个名字（虚假两难），四条同义条目占三格（乞题／循环论证／预设结论）；而与此同时同名异义大量存在。没有裁决规则。

**第三，机器做不到闭环。** 232 类细粒度分类最好模型约 34%；按语用辩证十规则分类，真实语料 0.23–0.29；把规则讲给模型听，性能反而下降。FAINA 数据集干脆设计成「承认多解」，因为两位受训专家会给出不同且都合理的标注。

三条合起来意味着：**任何输出单一判定的界面都在撒谎。** 唯一诚实的形态是把「用什么标准在衡量」交给用户选，并且让每套标准自带失效边界。

于是有了六副透镜。

## 二、六副透镜

| id | 名称 | 认为「论证出错」是什么 | 判定单元 | 原生刻度 | 主要失效场合 |
|---|---|---|---|---|---|
| `walton` | 论证型式与批判性问题 | 套用惯用型式的骨架，却没回答该型式的 CQ | 一条 CQ | 型式强度（抗 CQ） | 认不出型式；多型式混合；争议在前提真假 |
| `pragma` | 语用辩证十规则 | 某个言语行为违反使批判性讨论得以进行的规则 | 四阶段 × 一条规则 | 规则违反 | 广告、社论、独白——说话人不以解决分歧为目标 |
| `ars` | ARS 三标准 | 前提对该受众不可接受、或不相干、或不足 | 单个前提上的一个标准 | 三项独立符合度 | 三标准无阈值；受众未定时判不动 |
| `pta` | 型式周期表三特征 | 格子放错，后面所有评价都失焦 | 三个正交特征 | 定位一致性 | 中文口语主谓切不开；二阶尤易错 |
| `toulmin` | 图尔敏布局 | 担保没说出来，或撑不住那一跃 | 六要素之一 | 布局完整性 | 严格演绎里布局冗余；补出的担保是推定 |
| `copi` | 教科书名录对照 | （不判定）映射到传统名录条目，供教学对照 | 名录条目 | 条目匹配度 | 作为判定工具。它就为此而存在：展示名录法的极限 |

注意最后一行。`copi` 是全应用唯一一副**明确拒绝给出结论**的透镜。它的存在不是为了提供判决，而是让用户亲眼看到「贴标签」这条路会给出什么、以及它漏掉了什么。程序层面强制：该透镜下 `verdict.level` 恒为 `undetermined`，`whatIsRefuted` 恒为 `nothing`（守卫 G1）。

## 三、三层数据契约

`src/shared/types.ts` 把「与理论无关」和「与理论绑定」的部分彻底分开。

```
Diagnosis
├── context / scope            ← 共享：语境坐标 + 透镜适用范围自评
├── conclusion / premises / intermediate   ← 共享：重构结果
├── checks: CheckItem[]        ← 统一：六副透镜都归约成「检查项 + 回答」
├── lens: LensDetail           ← 分区：walton | pragma | ars | pta | toulmin | copi
├── defeat / verdict / repair  ← 共享骨架，verdict 同时保留原生刻度与归一化档位
├── labels / legitimateMoves / refutations
└── selfCheck / diagnostics
```

### 为什么 checks 必须统一

这是本应用的架构主张，也是它唯一可能做对的地方：**六套理论互不相容，但落到可执行层面，都能归约成「一组检查项 + 每项的回答」**。差值在「问什么、问多细、答完怎么算」，不在结构。

统一之后，三个东西才成立：
- 界面只需要一套检查表组件；
- 程序可以做确定性裁决（见下文 G2、G7）；
- 用户可以跨透镜比较「同一处地方在哪副透镜下被问到、在哪副透镜下根本没被问」。

`answer` 只有四个值：`passed | violated | unanswered | not-applicable`。语义按透镜不同，但结构相同。**`unanswered` 是完整答案，不是缺口**——它表示「文中无从判断」，比硬答 yes/no 诚实得多。

### 为什么 lens 不能压成一个字段

型式法的族与型式、PTA 的三特征、图尔敏的六要素、名录的候选，这四样东西不可通约。压成一个 `schemeId` 会立刻失真：PTA 允许「三个特征都定了但型名给不出」，单值字段无法表达这种状态。

所以分区存放，每副透镜一个 `kind` 判别联合。界面按 `kind` 渲染不同面板。

### 归一化是有损的，所以两套刻度都要留

`verdict` 同时存：
- `scale` / `scaleValue`：该透镜自己的话说出来的评级（「CQ2 未答，属削弱性击败」）
- `level`：归一化后的四档（`withstands | weakened | fails | undetermined`）

界面必须同时显示两者，并给出该透镜下这一档的具体含义（`THEORIES[].levelMeaning`）。只显示归一化档位，等于把六套理论压成一个仪表盘——那正是这个产品要反对的事。

## 四、提示词怎么装配

```
src/main/prompt/
├── common.ts        内核（与理论无关）+ 装配函数
├── fragments.ts     透镜模块契约：六项必填
├── index.ts         装配入口（注明顺序的理由）
└── lenses/
    ├── walton.ts    + 型式与 CQ 索引（22 型）
    ├── pragma.ts    + 十规则索引
    ├── ars.ts       + 三标准参考表、论证负担三档
    ├── pta.ts       + 三特征判定参考
    ├── toulmin.ts   + 六要素速查、六种担保类型
    └── copi.ts      + 名录索引（39 条）、名录自身病理
```

装配顺序：

```
内核 → 本次透镜（世界观）→ 判定程序 → 硬约束 → 范围门
     → 共享 JSON 骨架 → 检查项规格（含本透镜的 answer 语义）
     → 本透镜的 checks/lens 字段 → 本透镜索引 → 交付前四道检查
```

顺序不是排版问题。**范围门放在 JSON 之前**，因为模型写 JSON 时已经需要决定 `applicable`；放在后面，它会先把 JSON 编完再回头补一句「不适用」。

### 每副透镜必须提供的六样东西

`LensFragment`：`worldview` / `procedure` / `rules` / `scopeGuard` / `checksSpec` / `lensShape`，外加可选的 `index`。

缺一样不许上线。判定依据是：**六份模块之间不得互相引用，任何一段写进去的话都必须只属于这副透镜。** 换到另一副透镜下，它就会变成错误指引。这是检查提示词质量的第一条标准。

实际检查过一次：早期版本的内核里有一个 CQ 例子（「CQ2 领域相关性未答」），它污染了另外五份提示词——语用辩证透镜被要求用 CQ 术语回答。已改成透镜中立的表述（「没回答『他是否属于这个领域』」）。同类问题还出现在 `CHECK_SPEC` 里：原本一次性列出五种 `answer` 语义，现在按透镜只注入一条。

导出与自检：

```bash
npm run prompts     # 生成 docs/prompts/{walton,pragma,ars,pta,toulmin,copi}.md
```

脚本会对每份提示词做索引隔离检查（只应命中本透镜的索引标记），并输出字符数与行数。目前六份在 10.2k–14.3k 字符之间（型式库扩到 22 型后 walton 最长）。

## 五、程序层的十道确定性裁决

模型会越界，以下十类越界可以被代码抓住，且必须抓住。每一类都往 `diagnostics` 写一条——**静默修正是另一种撒谎**。

| 编号 | 越界 | 处理 |
|---|---|---|
| G1 | 名录透镜给出了终局判定 | 强制打回 `undetermined` / `nothing` |
| G2 | 范围门判不适用，却仍给了检查项 | 清空 checks。不适用的尺子量出来的刻度是假的 |
| G3 | 削弱性击败写成「结论为假」 | 改回 `argument-only` |
| G4 | 命名缺门槛（成立条件／何时合法／误判风险，缺一） | 该条目不予显示 |
| G5 | 型式 id 不在库内 | 降为 `none` 并留痕 |
| G6 | 检查项 system 与透镜不符 | 改正为当前透镜的 system 并留痕 |
| G7 | 固定清单未列全（十规则／六要素） | 补齐为「本次分析未覆盖」，**不假装已通过** |
| G8 | 不给档位的模式（查谬误／重构／提问）给出了档位 | 打回 undetermined，并留痕说明这是模式定义而非解析错误 |
| G9 | 同一句既被当作依据，又被当作中间结论 | 合并为一步，并按同一张对照表改写正文里的旧编号 |
| G10 | 判为适用，却一条结论都没抽出来 | 清引文并打回 `undetermined`。适用意味着能判，判没有落点 |
| G11 | 查谬误模式的命名没有位置 | 丢弃该条目并留痕，说清丢的是哪一条、缺的是位置还是落点 |

G7 值得单独说。如果模型只评了十条规则里的六条，剩下四条绝不能留空——留空会被读成「没问题」。补齐时 `answer` 填 `not-applicable`，`basis` 写死「本次分析未覆盖此项，不代表它已通过」。

G10 是自检接进生产之后才有的。它抓到的第一份真实报告是「你行你上」——语用辩证透镜判为适用，结论栏却是「未提出可检验的结论；字面语力」，引文却挂到了原文那四个字上。两件事不能同时成立，而界面把两件事都显示了出来。

G11 是加查谬误模式时一并加的。那个模式把名字当主输出，而名字最容易脱离位置单独存在。判据分两条，性质不同：位置（`quote` 且能在原文里定位）是硬要求，说不出是哪一句，名字作废；落点（`landsOnCheck`）只在**本透镜确实产生了检查项**时才要求——名录与 PTA 透镜按设计不产生检查项，这时候要求落点，等于让这两个透镜下的查谬误模式永远交白卷。检查项为空时不假装有条可落，改留一条 info 说明「这份名字只有位置、没有落点」。

## 六、新增一副透镜要改哪些地方

1. `src/shared/theories.ts` 加一条注册项（claim / unit / scale / appliesWhen / failsWhen / caveat / source / levelMeaning）。
2. `src/main/prompt/lenses/<id>.ts` 写六项必填。
3. `common.ts` 的 `LENS_MODULES`、`CHECK_SYSTEM`、`ANSWER_SEMANTICS` 各加一行。
4. `types.ts` 加一个 `XxxLens` 并挂进 `LensDetail` 联合。
5. `analyze.ts` 的 `normalizeLens` 加一个 case；若该透镜有固定清单，加进 G7。
6. `Diagnosis.tsx` 的 `LensPanel` 加一个面板。
7. `npm run typecheck && npm run prompts`，确认索引隔离仍通过。

不新增判断逻辑，只新增「问什么」。这是这套结构能容纳第七、第八副透镜的原因。

## 七、当前局限

- **一次只跑一副透镜。** `repair.alternativeReading` 与 `selfCheck.underOtherLens` 提供了跨透镜对照的文本，但没有并行跑两副再 diff 的界面。下一步最有价值的功能就在这里：同一段文本，两副透镜给出不同判定时，把差异本身作为结果呈现。
- **PTA 的中文落地未验证。** 主谓切分在口语里经常不成立，代码允许三个特征全 `undetermined`，但此时应视为透镜失效，而不是中性结论——目前只给警告，没有自动降级为 `applicable=false`。
- **`copi` 的候选上限硬编码为 3。** 若某段文本确实同时吻合四类，第四条会被静默截掉，只在 diagnostics 里体现。
- **提示词长度对上下文有压力。** 最长一份 14.3k 字符（walton，22 个型式的索引），约 6k token；加上原文与输出，单次分析在 9k–14k token 量级。若接 32k 上下文的小模型会吃紧。这也是为什么 `SchemeDefinition.criticalQuestions[].why` 只进界面、不进索引——它值一栏说明，不值 4k 字符的提示词预算。
