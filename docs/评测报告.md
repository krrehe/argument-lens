# 评测报告：二十三份真实语料

2026-11-01。工具自身的第一次系统性评测。

> **2026-11-03 补充，先说清楚这份报告的时效。** 语料已扩到 28 段（新增医院质控年报、合同条款、
> 项目复盘、学术评审意见、增长实验报告），并对全部 28 段按 18 类毛病逐条标注了覆盖。
> **新增的 5 段一次都没跑过模型**（账户余额为空），下面每一个数字——23 条、22 条有结果、
> 169,667 输入 token——仍然只属于 23 条那一轮。把这份报告当成「28 段的评测结论」是读错了。
> 语料覆盖的现状见 `npm run check:corpus` 的输出与 `scripts/eval/kinds.ts`。
>
> **2026-11-05 再补一句。** 语料又扩到 40 段（每类 ≥3 段、体裁互不相同、至少两种分析模式），
> 门槛也涨了。上面那句提醒因此更算数：**这里没有一个数字来自 28 段之后**。
> 门槛涨的是覆盖面，不是证据——那 17 段到现在仍然一次都没跑过模型。

这份报告不评分。评分会把「这段分析好不好」压缩成一个数字，而数字没法告诉你在哪一句上错了。
它做的是另一件事：**拿二十三份不同体裁的真实论证文本跑一遍，看它在哪些地方失效，失效长什么样。**

失效分三种，处理方式也不同：

- **结构失效**：报告自身前后矛盾、指向不存在的东西。代码能抓，抓到就不该再出现。
- **判断失效**：内容判错、条目选错、边界判错。靠提示词与知识库修，修完得重跑同一份语料验证。
- **边界失效**：它不是错，但它把用户留在一份没用的报告前面。靠界面修。

## 一、怎么跑

```
npm run eval        # 起一个 Electron 主进程，逐条跑真模型，结果落 scripts/.out/eval/
npm run eval:audit  # 只读结果，跑不变量与期望值检查，出审计报告
```

为什么不打分、也不接 CI：每条要调一次真模型，二十三条六分钟、十七万输入 token。
放进 CI 会让每次提交都花钱，而它测的又不是「有没有改坏」——那是 `check:*` 那套的事。
它测的是**提示词与知识库在真实文本上的表现**，只在改了这两样之后手动跑。

`cases.ts` 里每条样本都带 `traps`：这段文本里埋了什么。那不是给检查器看的，是给人看的——
跑完拿它对照报告，才知道「接住了没有」。

### 这一次的量

| 项 | 数 |
|---|---|
| 样本 | 23 条，13 种体裁 |
| 透镜 | 6 副全覆盖；模式 diagnose 18 / reconstruct 2 / redteam 2 / interrogate 1 |
| 输入 | 169,667 tokens |
| 输出 | 70,587 tokens |
| 累计等待 | 372 秒（单条 8–23 秒） |

### 结果

| 层 | 结果 |
|---|---|
| 不变量（破了就是 bug） | 0 条（修复后；修复前 5 条） |
| 提示（不一定是错） | 3 条：结论与依据共用一句原文 |
| 期望值（我写样本时的判断） | 1 条未达：社论被语用辩证判不适用 |

**一处残缺要说清**：23 条里最终只有 22 条留着结果。描写文那条在一次单条重跑时因账户余额不足失败，
而当时的宿主脚本会「失败时删掉旧产物」——把已经跑好的结果一起删了，且没法重跑。
这条现象（占位结论挂着原文引文）记在下面 A1，修复由 `check:contract` 的断言守着，不依赖那份 JSON。
宿主已改成「失败不销毁已有证据」。报告里引用的 token 总量来自完整的 23 条那一轮（169,667 / 70,587 / 372 秒），
审计脚本自己算出来的会比它少一条的量。

## 二、找到的失效

### A. 报告自己跟自己打架（结构，已修）

**A1. 判了不适用，结论栏写着「无结论」，却仍挂着原文引文。**

描写文那条样本上，结论栏是这样：`无结论：文本未提出任何可检验的主张`，而它的引文指向原文的`没有人说话。`
前半句说没有结论，后半句指着一句描写当引文。这不是措辞问题：**它让读者认定界面坏了**，而坏的是数据层。
模型被判不适用时仍会顺手给结论找一个 quote，代码从来没管过这个组合。

> 修：`normalizeDiagnosis` 里，判不适用且结论是占位文字时，清空 `quote` 与 `span`。
> 断言：`check:contract` 新增「判不适用时的占位结论不许挂原文引文」。

**A2. 同一句话既当依据，又当中间结论。**

学术摘要那条：`P3`「职业教育扩张会通过挤占优质师资……」与 `I1`「职普比提高导致本科上线率下降（因果成立）」
指向原文同一句。结构图上于是多出一级：读者以为结论被两级撑着，实际只有一句原话。

> 修：新增 G9——同一 span 出现在依据与中间结论里，合并为一步，并按同一张对照表改写正文里的旧编号。
> 为什么必须改写：合并之后 `defeat.cuts` 里那句「P1、P2 到 I1」就指向不存在的东西，
> 读者在图上找不到 I1，会以为漏画了一级。**修 A2 立刻制造了一个新 bug，这是同一件事的两半。**

**A3. 同一个谬误名出现两次。**

「张医生不可信，因为他做过药企顾问，而且说话傲慢」被给成两个「针对人身」候选。
界面上两个一模一样的标签并排，用户会以为有两处问题要回应。

> 修：按条目 id 去重，留第一条并留痕。

**A4. 判不适用时仍提示「没找到『此处合法』」。**

那条提示的用意是防清单法偷懒，它假设「有论证可评」。在描写文上，它把一句免责声明写成了指控：
用户看到的是一条暗示「可能没认真找」的黄条。

> 修：范围门判不适用时不再发这条。断言：适用时仍要发（两向都测，只测一边等于没测）。

### B. 判错了，而且错得有规律（内容，已修）

**B1. 名录缺了整整一类：靠来历与年岁定真假。**

伪科普那条样本的主干是「古人云药食同源」「中国人吃了几千年」，而 36 条名录里**没有诉诸传统，也没有起源谬误**。
模型只能把它们硬塞进相邻条目：一次判成「诉诸权威 / 诉诸公众 / 针对人身」，最显著的那一条整个漏掉。

这不是模型不听话，是**库里没有那个名字**。名录偏重「结构类」谬误（哪些推理形式不对），
缺「来源类」（靠来历、年岁、新旧定真假），而后者在真实文本里极常见。

> 修：补三条——诉诸传统、起源谬误、诉诸新潮，共 39 条。重跑同一条样本，三个候选变成
> 「诉诸传统 / 仓促概括 / 起源谬误」，条件也全部写得出。并把索引表头的「36 条」改成 `${FALLACIES.length}`。

**B2. 命名方向反了。**

「张医生不可信，因为他做过药企顾问」被判成「诉诸权威」。可这段话是在**贬低**权威，不是**诉诸**权威。
条件写得再齐，名错了就是把读者指向错误的反击点。

> 修：名录透镜加三条命名规则——先分清攻击的是命题还是说话人；利益冲突与人身属性必须拆成两条候选；
> 「古人云」这类不许当背景放过。重跑后「诉诸权威」消失。

**B3. 提示词里的数字与库对不上。**

型式索引写「22 个」，库里实际 23 个。这类漂移不报错，只是让模型在读索引时收到一个错误的总数。

> 修：两处都改成 `${SCHEMES.length}`。这条属于「文档比软件自信」的变种，只是这次漂在提示词里。

**B4. 同一段数学证明，两次跑出相反的范围门判断。**

第一次：「适用，六条 CQ 全部通过，withstands」。第二次：「不适用，演绎封闭，没有 CQ 可问」。
两种说法各自都讲得通——**说明规格没定，不是模型不稳**。用户看到的是：同一段证明，同一副透镜，
今天判合格，明天说没法判。而「修订对照」这个功能的前提正是同条件可复现。

> 修：把口径写进 walton 的 `scopeGuard`——形式化演绎证明判不适用，`alternativeReading` 指向 ARS。
> 重跑一致。**代价要说清**：用户贴一段证明进来，会看到「这副透镜在此不适用」。这句是对的，
> 但它听起来像「我没法看」，而实际是「这把尺子量不了这个，换那把」。

### C. 报告是空的，还不告诉你下一步（界面，已修）

社论那条样本选了语用辩证：文本是独白式评论，没有对手方，十规则里有几条根本无从谈起。
模型判「不适用」——这个判断站得住。但结果是：整份报告只剩结构图和零条检查项，
顶部一条红横幅说「不适用」，然后就没了。

模型其实写了出路，就在 `repair.alternativeReading` 里：「换用型式法或 ARS，那两副不要求有对手」。
只是它被埋在页面最底部的修补栏，而用户此刻正站在页面顶端，看着一份空报告。

> 修：横幅里增加一段「换一副透镜」，直接显示那句 alternativeReading；
> 「逐关检查」不再渲染一张空表，改成一段说明（不适用的尺子量出来的刻度是假的，所以这里空着是有意的）。
> 预览里加 `?oos=1`，让这一屏以后能被看见——**看不见的状态等于没测过的状态**。
> 截图：`docs/screenshots/scope-out.png`。

### D. 测试在用户的钱包和配置里留下了痕迹（工具链，已修）

这一条不是语料跑出来的，是准备下一轮时读脚本读出来的。它比前面几条都严重，因为它伤的不是报告，是人。

**D1. `npm run smoke` 会删掉用户的 API Key。**

冒烟的做法是：把测试配置写进 `%APPDATA%/argument-lens/settings.json`（**真实目录**），跑完在退出钩子里
`rmSync` 掉——注释写的是「测试配置必须清掉，留着会让用户下次打开时指向一个不存在的本地服务」。
这句话本身没错，但它删的是同一路径下**用户的**文件。于是「跑一次构建检查」等于「清空 Key 配置」，
而且只在脚本分支里发生，源码里完全看不出来。

**D2. 评测把二十三条报告写进了用户的历史，十七万 token 记进了用户的用量账本。**

`runAnalysis` 会存档、会记账，而它不知道自己在被测试调用。用户打开「历史」会看到二十三份没跑过的报告，
打开用量面板会看到一笔不是自己花的钱。**一个用来判断「这份分析可不可信」的工具，
自己的测试数据污染了它的账本——这比账算错更难看。**

> 修：两者都改用 `--user-data-dir` 指向临时目录，评测再把真实的 `settings.json` 与 `Local State`
> 复制过去（`Local State` 里存着 safeStorage 的密钥，只复制 settings 的话，密文解不开，
> 报的却是「尚未配置 API Key」——这个坑值得单独记一笔）。用户的配置、账本、历史一概不动。
> 跑完把复制过去的 settings.json 与 Local State 一起删掉：「为了读 Key 而复制一份 Key」，留在盘上就是第二份密钥。

**代价**：之前那一轮跑的账已经记进用户目录了，删不掉——也不能删，我没法把它和用户自己跑的分析分开。
这一条写在这里，作为「测试未隔离」的实物证据。

## 三、没修的，以及修不了的

**1. 独白式文本落到语用辩证上，报告仍然是空的。**
上面给了出路，但报告主体还是空的。这是设计选择——十规则要求有对手方，硬套会产出整齐的「未违反」，
那种干净是误判的产物。真正该改的是「用户为什么会选语用辩证」，那是选透镜的引导问题，不是这一轮的范围。

**2. 演绎证明没有一副透镜是它的主场。**
ARS 能评（前提可接受、推理有效、支撑充分），但界面上「换一副透镜」只是一句话，不会替他切过去。
一键切换是这个功能欠的最后一步。

**3. 覆盖率 33%–69%，而没有任何地方告诉用户「这些句子没进结构」。**
法律文书那条只覆盖 33%：裁判文书的「本院认为」段落里有大量程序性叙述，不进前提是对的。
但用户看不出「哪些句子被略过了、为什么」。这是一个已知的呈现缺口，不是判定的错。

**4. pta 与 copi 的 `checks` 恒为空，是设计，但极易被读成「没检查」。**
我第一版审计就把这条写成了 bug。改成说明文字之后仍然不理想：一个「0 项」的数字，
无论旁边怎么解释，都比不上一个真实的产出（pta 的识别结果在 `lens` 里）。

**5. 两次运行不完全一致。**
温度 0.2，同一个 prompt，CQ 数量在 3 和 6 之间跳动过。范围门是最不稳的一处（见 B4，已用规则钉住一处）。
这不是能彻底消掉的东西，只能靠「哪些判断必须稳定」的清单逐条钉。

**6. 名录 39 条仍是封闭清单。**
补三条之后覆盖面好了，但清单法的根本问题没变：**清单外的谬误形态拿不到名字**。
这也是名录透镜只给候选、不给判定的原因——它知道自己不全。

## 四、方法上的自我修正

审计把「我写错了期望值」和「软件判错了」放在同一张表里，这是这份报告最容易骗人的地方。
这一轮我有三处期望值是错的：

| 我写的期望 | 实际 | 谁错 |
|---|---|---|
| 裁判文书（pta）至少 3 条检查项 | 0 条 | 我错：pta 的判定形态是识别，不产检查项 |
| 描写文最多 0 条主张 | 1 条 | 我错：把占位结论算成了主张 |
| 数学证明范围门适用 | 不适用 | 都可辩护：真正的问题是两次跑不一致（见 B4） |

**所以「期望未达」不等于「软件错」。** 每次都要人工分辨，这一步不能自动化，也不该假装自动化。
表里那一条「社论范围门」至今挂着，我没有为了让报告变绿而去改它——它记录的是一个设计边界。

## 五、语料

十三条体裁，每条都在写的时候就知道答案长什么样。选材原则是「真实」而不是「典型」：
真实文本里数据是缺分母的、引证是占位符的、对手的立场是被概括过的。

| 样本 | 体裁 | 透镜/模式 | 文本里埋了什么 |
|---|---|---|---|
| academic-panel | 学术摘要 | walton / diagnose | 面板数据 + 控制变量被当成因果识别，没说用了什么识别策略 |
| philosophy-gettier | 哲学短文 | toulmin / diagnose | 论证靠思想实验的直觉，担保是「直觉在概念分析中可作证据」——这一条从不写出来 |
| legal-analogy | 裁判文书 | pta / diagnose | 类比推理：与（2016）民申字第 xxx 号「情形相同」，但没说出相似性为何在法律上重要 |
| ad-copy | 广告文案 | copi / diagnose | 「300 万家庭在用 → 更值得选」隐含「多数人的选择等于更好」 |
| news-attribution | 新闻报道 | walton / interrogate | 权威链条三级衰减；记者自己给了削弱材料，整段其实是质疑 |
| pseudo-science | 网络科普 | copi / redteam | 「吃了几千年从未听说谁生病」= 诉诸传统 + 诉诸无知 |
| non-argument | 描写文 | walton / diagnose | 通篇无主张；最容易出的错是硬造一个结论 |
| negotiation | 商务对话 | pragma / diagnose | 对话类型是协商，不是说服 |
| strong-argument | 规范论证 | ars / diagnose | 好论证：先说清对手读法，再给替代概念，结论带范围限定 |
| citation-density | 学术段落 | walton / reconstruct | 「研究表明，43%」是二手转述，从比例直跳「主因」 |
| tech-decision | 技术文档 | toulmin / diagnose | 「95% 是 4xx 所以重试无意义」——剩下 5% 的 5xx 最需要退避 |
| long-editorial | 社论 | pragma / diagnose | 三段独立论点共用一个结论；北欧类比未处理制度差异 |
| english-remote | 英文评论 | walton / diagnose | 用研究设计缺陷反驳调查，但替代证据的样本同样有限 |
| math-proof | 数学证明 | walton / diagnose | 纯演绎；「p² 偶则 p 偶」是未写出的引理 |
| quote-rebuttal | 论辩短文 | toulmin / diagnose | 引号里是他人的话，作者在拆它；作者的结论极窄 |
| stats-brief | 政策简报 | walton / diagnose | 死亡人数降 18%，分母全没给 |
| ambiguous-referent | 会议纪要 | walton / reconstruct | 「不予采纳」的宾语有两个候选，两种读法方向相反 |
| personal-appeal | 个人陈述 | toulmin / diagnose | 情绪开场，中间有一条真的规范前提 |
| self-defeat | 评论片段 | toulmin / diagnose | 用单例宣布一条全称命题不重要 |
| ad-hominem-real | 网络评论 | copi / diagnose | 利益冲突（相关）与人品攻击（无关）混在一句 |
| medical-consult | 会诊记录 | pragma / diagnose | 共同求解而非说服；「不能排除」是保留判断，不是主张 |
| history-inference | 历史论证 | walton / diagnose | 溯因；「同期无其他记载」是消极证据，力量取决于记载完备程度 |
| p-hacking | 研究评论 | walton / redteam | 八个亚组两个显著；探索性结论被写成确证性结论 |

### 加一条语料要守什么

1. **文本必须是真实的**。不为测试编造病句——真实文本里该有的毛病（缺分母、占位引证、概括对手）本来就够多。
2. **必须写 traps**。写不出「这段话里埋了什么」，这条语料只是在测模型随机性。
3. **期望值只写有把握的**。宁可留空，不要把自己的猜测写成标准答案。
4. **加完必须真跑一遍**，因为陷阱和实际输出经常对不上——这一轮三条期望值就是这么错的。

## 七、下一轮该测什么

这一轮的盲区很清楚：

- **长文本**：最长 1,000 字。`MAX_LEN` 是 15,000，切分与「整篇送进去会怎样」完全没测。
- **注入**：没有一条样本在文本里写「忽略以上指令」。输入隔离是安全属性，不测等于没有。
- **同一文本的多次运行**：这一轮只有数学证明跑了两次。一致率是「修订对照」的地基，该专门量。
- **模型更换**：全在 deepseek-chat 上跑。换成别的模型，B1/B2 那类内容失效大概率会变，而结构失效不该变——**这正是区分「提示词问题」与「模型问题」的办法**。

还有一条不是盲区，是现状：写这份报告时账户余额用完了（402 Insufficient Balance）。
这一轮前后跑了五轮完整语料，约八十多万输入 token，余额见底。这本身就是评测的一个属性——
**它要花钱，而且不是象征性地花**。`npm run eval` 不该进 CI 的另一个理由就在这儿：
一个按提交频率自动烧钱的任务，最后一定会被关掉，关掉之后就没人记得它测过什么。
