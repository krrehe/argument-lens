# 路线图

这份文档回答一个问题：**接下来该做什么，不该做什么。**

它不列功能，因为功能不缺。它按「消灭哪个未知」排序，而不是按「哪个功能大」排序——一个长期项目的死法，通常不是功能不够，是力气花在了已经知道答案的地方。

---

## 一、现在的处境

三组数字能说清：

| 事实 | 数字 |
|---|---|
| 代码规模 | `src/` 下 73 个 TS/TSX 文件、23,881 行 |
| 断言规模 | 静态约 2,204 条（lint 666 / 样式 640 / 学术 152 / 落点 107 / 理论 102 / 契约 81 / 语料 63 / 稳健性 54 / 相似度 50 / 导出 47 / 重放 45 / 处方 34 / 示例 34 / 文档 33 / 快捷键 28 / 记账 26 / 自检 22 / 对照 20），另加端到端四组：基础 46、进行中 5、按停 14、示例 10 |
| 真实用户数 | **1**（102 份报告、**6 组不同文本**，其中 **99 份是同一段「取消早读」的四个版本**——89 份逐字相同、8 份加了两句、1 份删到只剩开头、1 份改写成提纲；14 份带模型原文） |

**工程质量远超产品验证。** 这不是自谦，是一个具体的不平衡：两千条断言证明的是「界面上该出现的东西出现了」，而「判断对不对」只有 28 条语料、一家模型、六分钟、十七万 token 的评测在管。

那份评测进不了每次改动，因为它要花钱（现在余额为空）、要六分钟。**但「改动之后报告变了，是谁变的」这个问题已经答得了**：P0-1 让每份报告存下模型原文，P0-2 的 `check:replay` 拿它离线重跑解析与十一道裁决，0.8 秒、不联网。所以现在分得开两件事——代码改坏的（重放会红），和模型换了说法的（重放不动，只有 `eval` 看得见）。

剩下的不平衡在产品那一侧，而且不在工程量上。2026-11-03 重新数了一遍存档，比原来那句「89 份是同一段」更准确：**102 份报告落在 6 组文本上，其中 99 份是同一段「取消早读」的四个版本**（89 份逐字相同、8 份加了两句、1 份删到只剩开头、1 份改写成提纲）。**同一个样本跑一百遍，得到的是一百份报告，不是一个样本的一百次验证。**

这也是这一轮做了两件事的原因：示例从一段改成六段——按钮本身在教人反复试同一段；输入框下面加一行「这段跑过没有」——同一段文字再跑时，把「已经跑过 89 次」摆在按下去之前。两件都是同一个判断：**这个软件此前从不告诉人「你其实只试了一种文本」。**

所以下面四个阶段里，P0 全部是零成本的工程活，P1 要一点钱，P2 只有你能做，P3 在 P2 有答案之前一概不碰。

## 二、P0 · 让验证变便宜（0 元，最优先）

**要消灭的未知：改了代码之后，我怎么知道有没有改坏已有的判断？**

现在答案是「不知道」。P0 把这个问题变成「一条命令，几秒钟」。

### P0-1 保存模型原始输出

`Diagnosis` 加 `raw`：模型返回的原文，连同 `prompt.version` / `prompt.fingerprint` 一起落盘。

- 体积：一份约 8 KB（现在报告 12 KB），可接受
- 隐私：**没有新增暴露面**——`passage` 已经存了原文全文
- 顺带修一处：`prompt` 字段已经填了，但 87 份里只有 59 份有。旧存档不回填是对的（不造假版本），但**界面该在缺失时显示「未知版本」而不是空白**

做完这一条，报告就能自述「我是哪版提示词、由哪段模型原文解析而来」。

### P0-2 离线重放

**状态：已完成（2026-11-02）。** `npm run replay`：读存档里的 `raw`，本地重跑解析 → G1–G11 裁决 → 自检，
与存档逐字段比对，列出差异。不联网、不花钱、0.8 秒。

做出来的比原计划多一样东西：`check:replay` 进了 `verify`。原计划里这条命令要手动跑，
而「要手动跑的东西实际上从不跑」正是 P0 要消灭的那种状态。现在仓库里冻着六份基准
（`scripts/fixtures/replay/`：三份真实报告 + 两份构造的 + 一份假模型的查谬误，见下），每次 `verify` 都重放一遍。

**判据不是「零差异」。** 版本升级本来就该有差异。判据是：**每一处差异都能被解释**——要么是这次有意改的，要么是新发现的 bug。无法解释的差异，就是回归。

那么「解释」这件事怎么落到代码里？拆成三类，只有第一类算回归：

| 类别 | 例子 | 算不算回归 |
|---|---|---|
| 值变了 / 字段没了 | `verdict.level` 被削弱 → 判不了 | **算**，必须能解释 |
| 存档没有、现在有，但**是空值** | `labels[0].quote: null`（这一栏是后加的，旧代码在那处同样没内容） | 不算，但要列出来 |
| 运行时才决定的诊断 | `JSON_REPAIRED` / `TEMPERATURE_CLAMPED` / `PROMPT_OVER_BUDGET` | 不比对，写明为什么 |

第二条的边界必须收紧：只要新增的东西**有内容**（比如代码开始多报一条裁决留痕），就落回第一类。
松一档，就会出现一个很坏的洞——报告明明多了一条警告，检查却绿着。

**两份基准是构造的，得说清楚。** 真实那三份跑出来一条 G 裁决都没触发（模型很乖），
于是 `fx-g3-overrun`（把原文改成「削弱性击败被写成结论为假」）和 `fx-g6-system`
（把一条检查项的 system 改成另一副透镜的）是改原文做出来的。它们锁的是**当前行为**，不是正确行为：
哪天发现 G3 本身判错了，改完要 `--accept` 重新录，而不是让它红着。

**第三份不是构造的，但也不是真的**：查谬误模式那一份来自假模型。加它是因为模式要拉开——
G8 只在「不给档位」的模式里生效，而原先六份里五份都是诊断模式，把 G8 整段删掉也照样全绿。
这件事本身也写成了断言：基准必须同时包含「给档位」和「不给档位」的模式。
删掉一份基准能让检查变绿，是基准类检查的通病，只能用这种结构性断言顶住。

**它能验的边界**：只验「同一段原文下，解析与裁决是否稳定」，验不了模型下次会不会换个说法。
另外手里 101 份存档只有 13 份带 `raw`（该字段 11 月 1 日才加），旧报告的重放覆盖面是零——
这一点命令自己会打印出来，不用记。

### P0-3 一条命令跑完全部

`check:*` 散在 `package.json` 里，靠人记住。一个人维护的项目，**记不住的东西等于不存在**——
断言再多，跑不起来就是零。

`npm run verify`：类型 → 全部 check，一条命令一个退出码；清单从 `package.json` 动态发现，
新增的 check 自动纳入（硬编码的清单会静默漏掉后来加的那些，而它照常打印「全部通过」）。

另有 `npm run check:docs`：交接文档点名的命令与路径必须存在，`verify` 跑的每一关必须先写进 `AGENTS.md`
——**新增一条检查却没写进交接书，下一个会话就不知道它在**，这是文档版的假绿。

### P0-4 失败可见

**要消灭的未知：界面上说「成了」的事，是不是真的成了。**

这一类问题在代码审查里一次找出六处，共同点是**界面上表现为「什么都没发生」**：异议写不进文件、报告存不进历史、配置不合法照样保存、旧报告读不出来。用户点了一下，屏幕没有变化，他只能以为是自己没点中——而这类 bug 最难报，因为当事人说不清发生了什么。

四条规矩：

1. **写失败一律往上抛。** 抽 `src/main/jsonl.ts`（不 import electron，于是检查脚本能在纯 node 里造一个写不进去的路径真跑一遍），IPC 层把异常翻成 `ok:false` + 原因。
2. **失败与结果分开显示。** 报告照给（钱已经花了），但报告顶上多一条「有一件事没做成」；混进错误条里会让用户以为报告是坏的，而报告是好的。
3. **每个空 catch 必须写 `@allow-silent:` 与理由。** 允许静默，不许不留据。`check:robustness` 扫描 `src/main` 与 `src/renderer/src`，抓到没写理由的空 catch 就红。现在 5 处，每处都写明了为什么可以静默。
4. **凭据不回读。** `settings:get` 不再返回解密后的 Key 明文，只回「有没有 / 解不解得开」。为让输入框显示出来而把凭据复制进渲染层，换来的好处顶不上那条通道。

顺带收紧的两处：渲染进程开 `sandbox`（preload 只用 `ipcRenderer` 与 `contextBridge`，关掉沙箱换不来任何东西，只把 node 运行时留在了渲染层一侧）；模型报错回显走 `briefOf`，截到 160 字并抹掉 `sk-` / `Bearer` 片段——有些网关会把请求头原样回显。

### P0-5 每一屏都被人眼看过

**要消灭的未知：界面上那些「只存在一会儿」的状态，到底长什么样。**

P0-4 修的是「失败不可见」，那还可以从代码里读出来。这一条修的是另一类：**只在特定时刻出现的屏，没人见过**。它们不报错、不影响构建，代码读起来也像对的——只有把它拍下来才会发现问题：

- **分析进行中**（30–90 秒）：主区显示的是首屏空态「先给一段真话」，而用户刚刚贴了文本、按了按钮；阶段名算出来却没人显示。
- **按了分析之后的按钮**：文案是整句阶段名，把按钮撑成三行，顺带把「128 字」和「填入示例」各挤成两行。
- **设置页**：这一屏要读 IPC，静态预览页跑不了，于是从来没被截过图。首次启动的引导版正是它。
- **保存被拒**：同一句错误在正文末尾与按钮上方各显示一次，相隔 40 像素。

处置办法不是「以后注意」，是给每一屏留入口：

1. 预览页支持 `?running=<阶段>&wait=<秒>`、`?dlg=settings[&onboard=1][&bad=1]`，`bad` 会自动替人按一次保存，让校验失败那一行进入画面。
2. 端到端加 `MOCK_DELAY_MS` + `SMOKE_RUNNING=1`：把假模型的响应拖住 4 秒，然后断言三件事——面板出现而不是空态、阶段名来自主进程（不是写死的占位）、**「已等」在走**（隔一秒取两次，第二次必须更大）。只截图不断言，等于给坏掉的界面留了张好看的证据。
3. 反向验证两条：停掉计时器 → 「已等」那条红；拿掉面板 → 四条全红。

### P0 完成的样子

改完代码，`npm run verify` 三分钟内给出「可以/不可以」，且「不可以」时会指出是哪个已有报告的那一栏变了。到这一步，后面所有阶段才有讨论的基础。

## 三、P1 · 语义质量的最小证据（小额，我做）

**要消灭的未知：报告的内容到底准不准。**

### P1-1 语料扩到「每个陷阱至少两条独立文本」

现在 28 段、18 类毛病，**每一类至少两段不同体裁、字面不像的文本**（`check:corpus` 守着）。不追求 100 条——**数量不是问题，覆盖的独立性才是**。同一段文本跑 82 遍得出的是 82 份报告，不是 82 个样本。

目标：约 40 条，每条陷阱由至少两段**体裁不同、措辞不同**的文本触发。判据：一条陷阱只有一个样本时，无法区分「软件抓到了」和「这段文本太典型」。

### P1-2 跨模型一致性

同一组语料，用两个模型跑，比对：型式识别、档位、检查项 answer。

这一步同时是两个问题的答案：
- **质量证据**：差异率高的字段，说明软件把它当结论的地方其实不稳定
- **模型换代的对冲**：如果整个价值都随模型浮动，那么「换模型就归零」是真的；如果有相当一部分字段跨模型一致，说明那部分价值来自软件自己（本地规则、静态表、结构约束）而不是模型

差异率超过 30% 的字段，只有两条出路：**用本地规则压住**，或者**在界面上标为「需人工确认」**。不许继续当作确定结论显示。

### P1-3 判定手册 + 一次独立标注

把「什么算型式认对」「什么算过度诊断」写成可复核的条目，找一个人独立标 20 份，算一致性。

**不追求一致性高。** 追求的是**知道它有多低**。如果两个人看同一份报告得出不同结论，那问题不在模型，在报告的表达——这比分析错更严重，因为它意味着报告不可判读。

## 四、P2 · 真实使用（只有你能做）

**要消灭的未知：谁在用它，用完之后做什么。**

10 段你自己的、真实的、没为这个软件准备过的文本。跑完只记录一件事：**看完报告之后的下一句话是什么。**

- 「哦，原来我这里是这个问题」→ 诊断成立，继续加深度
- 「所以呢」/「然后我怎么改」→ 处方层还不够，或者形态不对
- 「它说错了」→ 语义质量还有硬伤，回 P1

这件事我做不了，也不需要花钱。它是整份路线图里信息量最大的一步。

**已经为它做的一件事**（2026-11-01）：报告可以导出成 Markdown——带判定与限定、原文引文、下一步的可勾选清单。理由很直接：如果用户的工作是在 Word 里改稿，那么「回应用看一眼报告」本身就是一个很高的门槛，而 P2 要观察的恰恰是「看完之后做什么」。带不走的报告，连被使用的机会都没有。

但导出本身不是答案，它只是把 P2 的门槛降低了一格。**没有真实文本跑过之前，不要因为它好用就以为它有用。**

## 五、P3 · 产品化（等 P2 有答案再谈）

安装、升级、崩溃恢复、首次引导、多语言、错误上报。这些只在「有第二个人用」时才有意义。**在 P2 之前做这些，是把力气花在给一个还没验证的东西修门面。**

## 六、不做清单

长期项目最容易死在不断加东西上。以下几条明确不做，附理由：

| 不做 | 理由 |
|---|---|
| **不加第七副透镜** | 六副是设计决定，不是待办。加一副会让「为什么是这六副」这个已经回答过的问题重新变成问题 |
| **不再加检查断言** | 已 1900+。新增断言只能保护新增代码，不能提升判断质量。**断言过剩会制造虚假的安全感**——绿色变多，真问题变少被发现 |
| **不做云同步 / 账号** | 会毁掉「本地运行、密钥自持、报告不出机器」这个立场。这是它相对在线工具唯一的硬优势 |
| **不扩谬误名录** | 39 条到 40 条不改变任何人的体验。名录的边际收益早已见底 |
| **不做 Web 版 / 移动端** | 同上，除非 P2 证明有人要用 |

## 七、节奏

一次会话做一个**能被断言证明完成**的块。一个块 = 一次提交 + （若碰了源码）一次重打包。

不要按里程碑排，按块排。里程碑会在中途变形，块不会。

建议顺序：P0-1 → P0-2 → P0-3 → P0-4 → P1-1 → P1-2 → P1-3 → P2 → 再回到 P1/P3。

P2 不必等前六块全做完，它不依赖任何代码，随时可以开始。

---

## 八、什么情况下该掉头

规划的另一半是承认失败的条件。写在动手之前，才不会被沉没成本绑架：

- **P2 的 10 段文本，多数人的下一句是「所以呢」** → 问题不在分析深度，在形态。该考虑从「出一份报告」改成「陪你改一遍」——那是另一个产品，不是这个产品的下一个版本。
- **P1-2 跨模型差异超过 50%** → 说明报告的结论主要来自模型的临时发挥。该收缩承诺：少说，但说得准；把「确定」的部分与「模型认为」的部分在界面上彻底分开。
- **半年内 P2 无法完成** → 承认它是个人工具。停止 P3，把维护成本降到最低（只修 bug，不加功能），这也是一个体面的结局。
