# 理论主张库

> 一句话：把十编散文拆成一条条能被单独指认、单独质疑的主张，每条都标明它有多硬、以及它让本工具做了什么。

## 一、为什么还要加这一层

在这之前，这个项目已经有三层「凭什么」：

| 层 | 回答什么 | 位置 |
|---|---|---|
| 术语表 | 这个词什么意思 | `glossary.ts` |
| 理论卡 | 这副透镜凭什么成立 | `theory-notes.ts` |
| 十编文档 | 每条规则背后的争论与出处 | `docs/理论支撑/` |

三层都做完了，链条上仍有一处断点：**理论卡是一副透镜一张，粒度太粗**。一副透镜背后有七八条互不相同的主张，而这张卡只能笼统地给出「道理在哪」。用户读到「按 RSA 三标准判」，再问一句「三标准本身凭什么」，卡片答不上来——它给的是整副透镜的根据，不是这一条的根据。

第四层补的就是这个：把十编拆成可引用的条目。

## 二、一条主张必须回答三件事

`src/shared/theory-base.ts` 里每条有四个必填字段，其中三个是实质要求：

| 字段 | 要求 | 不合格的样子 |
|---|---|---|
| `claim` | 一句话说清它主张什么，去术语 | 「论证具有可废止性」——术语，外行读不懂 |
| `tier` + `refs` | 它有多硬，出处可查 | 「研究表明……」——没有具体文献 |
| `decides` | **它让本工具做了什么** | 「应当重视前提的可靠性」——没有落点 |

第三条是硬要求，也是这个库与文档的分界线。**一条主张若指不出它在代码里改变了什么，它就不该进这个库**——那是文档，不是依据。

反过来说，代码里任何一条判定都应能在这里找到依据。找不到的地方，就是理论没做实的地方。这句话是这张表存在的真正理由：它是一个自查工具，不只是给用户看的说明。

## 三、三档标注的判据

```
A 一手文献   能在具体文献里查到。这一档最硬，也最少。
B 学界通说   教材转述或通行说法。可靠，但没核到原文那一句。
C 本工具判断 这个工具自己的推论，可能是错的。写出来是为了让人知道该往哪儿打。
```

判据比名字重要，所以写细：

- **A 档**必须有「作者 + 篇名/书名 + 年份」，或者原作者本人写明的限定。比如「van Eemeren & Grootendorst 自己写明十规则只在以解决分歧为目标时适用」算 A，因为那是作者本人的范围声明，不是别人的解读。
- **B 档**是「教材都这么讲，但我没核到原文」。这种情况下写「Walton 关于 burden of proof 的论述」而不是编一个页码。
- **C 档**必须写清依据什么推出来的。写「本工具的判断」四个字就完事的，不合格。

三条硬规矩：

1. **C 档不许标成 A 档。** 这是整套标注唯一可能被蓄意破坏的地方，也是最容易无意中破坏的地方——写的时候总觉得自己的推论「当然是通说」。
2. **「研究表明」没有具体出处，一律降为 C。**
3. **宁可少一条，不编一条。** 库里没有某条主张，读者看不出缺什么；库里有一条编的，读者信了它，就比没有更糟。

## 四、档位分布是诚实的，不是谦虚

当前 102 条里，A 档 27 条、B 档 48 条、C 档 27 条。**后两档加起来比第一档多。**

这不是设计缺陷。一个论证分析工具里，真正能追到原文的规定只占少数，其余是有理由的推论与工程取舍。

第八至十编（批判性思维、哲学与人文视野、其他论证传统）有一半主张落在「不做什么」上：不评动机、不声明视角、不按领域换标准、不回查自己。「不做」在这个库里是合法落点——指得出是哪条设计决定、理由是什么、谁会反对，就比「还没做」强。第七编整编都是 C 档，因为它是工程判断编（`THEORY_BOOKS` 里标了 `engineering`），check:theory 认这个标记：不标标记却整编 C 档，等于把工程判断摆在文献编的排场上。把 C 档 27 条标成 A 档，会让这个库看起来很硬——然后每一条都经不起追问。分开标出来，读者才知道该信到哪一层。

界面上的处理与此一致：**C 档不做视觉降级**。三档用同样大小的徽标，只是颜色不同。若把「本工具判断」排成灰色小字，等于暗示它不重要——实际正相反，那是最该被反驳的部分。

## 五、与「争议」的关系

两个库容易混，区别在这里：

| | 理论主张库 | 争议库 |
|---|---|---|
| 单位 | 一条主张 | 一个分歧点 |
| 说的是 | 「我认为 X，依据是这个，落点是这个」 | 「X 与 Y 两派在争，本工具站 X，代价是……」 |
| 有没有对手 | 可以没有 | 必须有，且至少两派 |
| 用来做什么 | 追问依据 | 知道该攻哪里 |

一条主张可能对应一条争议（比如「可接受性看受众」对应「受众相对」那条），但不必强绑。绑定关系写在主张的 `contested` 字段里，是自由文本——因为有的主张有反对者但够不上「学界两派分立」，强行给它编号反而夸大。

## 六、这一层不能干什么

1. **不能证明本工具是对的。** 列出依据不等于依据成立。C 档那 24 条，随时可能是错的。
2. **不能代替读原文。** 索引的用处是知道该去读哪一篇，不是替代那一篇。
3. **不能自动更新。** 主张与代码是两份东西，会脱节。见下一节。

## 七、已知问题：它会脱节

这是结构性问题，不是疏忽。

改了一处判定逻辑，理论上要同步改对应的 `decides`。但没有机制强制这件事——类型检查管不到语义。三种脱节方式：

- **代码改了，主张没改。** 表现是「它让本工具做了什么」描述的行为已经不存在。最隐蔽，也最有害。
- **主张加了，代码没动。** 表现是一条主张指向一个不存在的字段。`check:theory` 能抓住这一类的相当一部分：decides 里写下的代码标识符必须真的存在于 src/（排除库文件自己——主张写什么库文件里就有什么，幻影字段在原地当然「找得到」）。这条检查上来之前，库里真有过三处写着不存在的字段。它仍抓不到「字段还在、语义已变」的那类。
- **两边都改了但方向不一致。** 最难查。

第十七轮加了一层：**落点表**（`src/shared/landing.ts`）把「这条主张落在哪」从一句话变成四个可解析的地址（`block:` / `lens:` / `code:` / `ui:`），`check:landing` 逐个验它存在。这让第一、二两种脱节多了一道闸：

- 块改名、透镜片段被清空、函数改名、界面区块改名 → 当场报错，而不是等到有人读文档时才发现；
- 一条主张若真找不到落点，就写不进这张表——而表要求每条至少一处；
- 地址写错（少一级目录、指到不存在的类型）同样会被抓出来。这次就是被它抓到的：库里引用的 `CriticalQuestion` 这个类型从来不存在，真名是 `SchemeDefinition.criticalQuestions[]`，而 `check:theory` 里恰好有一张白名单把它护了十几轮。

仍抓不到的：**地址还在、但那一处做的事已经变了。** 这与 check:theory 的最大弱点同源。唯一的延缓办法是把 `at`（「在那一处变成了什么」）写具体到能被反驳——「影响报告措辞」这种写法，检查器只能判它太短，判不了它是不是真的。

能做的还有一件事：**把两者放在同一个仓库里，改代码时看得见它**。这一条写进了 README 的结构说明，也是这个库没有单独开仓库的原因。

发现脱节的最后一道防线仍然是人工对读。`docs/理论支撑/07-理论到代码.md` 第十节那张表由 `landing.ts` 生成，改代码时过一遍。

## 八、怎么加一条主张

1. 先问：它改变了哪个字段、哪条裁决、哪个行为？**答不出就不要加。**
2. 定档：能追到具体文献吗？不能就写 B 或 C，不要犹豫。
3. 编号：`T` + 编号 + `-` + 序号。序号在编内往后排，**不改旧号**——旧号已经被别的文档引用了。
4. 写 `claim` 时念一遍：一个没上过逻辑课的人听得懂吗？
5. 如果它只影响某几副透镜，填 `lens`；影响全部就留空（留空 = 六副共用底座）。
6. 如果它对应某条争议，在 `contested` 里写上；没有就留空，**不要为了填而编一个反对者**。
7. 给它一个**细分域**（`sub`，20 个封闭取值之一）。编按「理论在回答什么」分，细分域按「话题」分——报告里的专题分析按这根轴取主张。新条目直接写 `sub` 字段；旧条目的取值集中在 `SUB_BY_ID` 一张映射表里。写漏了 `check:theory` 会响。
8. 写**落点**：在 `src/shared/landing.ts` 里给它一个地址——提示词块（`block:core.gate-four`）、透镜片段（`lens:ars/rules`）、代码（`code:src/main/analyze.ts#resolveSupports`）、界面区块（`ui:Diagnosis.tsx#sec-limits`）。再加一句 `at`：**在那一处它变成了什么动作**。写不出就回头改第 1 条——那说明它确实没有落点。
9. 改完跑 `npm run check:theory` 和 `npm run check:landing`。前者验：id 唯一、档位不虚标、每个细分域至少有一条主张、每编有配套文档且整编 C 档必须标 `engineering`、decides 的落点真实存在、别处（如报告边界栏）引用的主张 id 必须真的在库里。后者验：每条有落点、每个地址真的存在、说明不是套话、主张与落点表两边对得上。两个检查器都做过反向验证：注入假文档路径、假 id、摘掉 `engineering` 标记、改坏四类地址，各自都会响。

## 九、界面在哪

- 顶栏「参考」里的「理论」按钮 → 主张库全文（搜索、按档与细分域筛选、按编分组）
- 侧栏透镜卡底部「这一栏专有的 N 条主张」→ 点一条直接定位到库里那一条
- 主张库末尾「附 · 语用辩证十规则」→ 十条规则各守什么、落在哪

这三个入口共用同一个数据源。改 `theory-base.ts` 一处，三处同时变。
