# 与画布工具互通：把结构交出去，而不是把工具塞进来

> 对象：[Project Graph](https://github.com/graphif/project-graph)（`graphif/project-graph`）。
> 检索与核对于 **2026-11-08**（GitHub API + 浅克隆 `master` + 用它的 CLI 实跑一次）。
> 这份文件只写**事实与判据**。进度不在这里，在 `docs/路线图.md` 末尾的阶段观察。

---

## 一、结论

1. **它的画布不能嵌进来。** 桌面应用本体是 **GPL-3.0**。这个软件要打成 exe 分发，
   链进 GPL 代码就得把整个项目按 GPL 开源——用户没同意过这件事。
2. **它的格式可以照着写。** `.prg` 是一种**文件格式**：zip 容器 + msgpack 数组 + 版本号。
   格式不是代码，写它不涉及复制实现。我们写的是自己的编码器（`@shared/prg-pack`），
   一行实现都没搬。
3. **兼容性不靠自己声明。** 两条证据：字节被 `@msgpack/msgpack` 与 `@zip.js/zip.js`
   （devDependency，不进包）读回同一棵树；以及**它自己的 CLI** 读过一份我们导出的文件，
   把 7 个节点、6 条线按我们写的位置与朝向读了出来（第六节原样摘录）。
4. **不做的事**：反向导入（读别人的工程文件来改一份报告）、嵌它的界面、替它做判定。

## 二、许可证事实

| 对象 | 许可证 | 能不能进 exe |
|---|---|---|
| 桌面应用（`app/`，即整个可执行体） | **GPL-3.0** | **不能**。分发即要求整体以 GPL 开放 |
| `packages/serializer`（`@graphif/serializer`） | MIT | 能，但没必要：它是个通用的「实例 → 对象」工具，不是 `.prg` 的编码器 |
| 仓库根 | **没有 LICENSE 文件**（GitHub API 报 `license: null`） | 逐目录看各自的 `LICENSE` |

结论与 `docs/融合清单.md` 里 logikon 那一条同一口径：**AGPL/GPL 一律不进包**。
区别在于这次连「只吸设计」都不必——要的是格式，格式可以照着写。

## 三、格式事实（`2026-11-08`，目标版本 `2.7.0`）

`.prg` 是一个 **zip**，条目如下（后四个可选，只缺 `stage.msgpack` 才算坏文件）：

| 条目 | 内容 |
|---|---|
| `stage.msgpack` | 一个数组：舞台上所有对象，`{ _: 类名, 字段… }` |
| `tags.msgpack` | 字符串数组（我们写空数组） |
| `reference.msgpack` | `{ sections: {}, files: [] }`（附件与区块引用，我们没有） |
| `metadata.msgpack` | `{ version: "2.7.0" }` |
| `README.md` / `attachments/<uuid>.<ext>` | 可选，我们不写 |

`stage` 里的两种对象（字段名与顺序都按对方测试夹具的写法）：

```text
TextNode   { _: "TextNode", uuid, text, collisionBox: { _: "CollisionBox", shapes: [Rectangle] },
             color: { _: "Color", r, g, b, a } }
Rectangle  { _: "Rectangle", location: Vector, size: Vector }
Vector     { _: "Vector", x, y }
LineEdge   { _: "LineEdge", associationList: [ {$:"/源下标"}, {$:"/目标下标"} ],
             color, targetRectangleRate: Vector(0.01, 0.5), sourceRectangleRate: Vector(0.99, 0.5), uuid, text }
```

几条容易写错的：

- **`{ $: "/3" }` 是数组下标引用**，指向**先出现过**的那一份对象。写连线时节点必须排在前面。
- **`Color` 的 `r/g/b` 是 0–255，`a` 是 0–1**（不是 0–255）。
- **`associationList` 的第一个是源、第二个是目标**；`sourceRectangleRate.x = 0.99`
  表示从源的右边缘出发，`targetRectangleRate.x = 0.01` 表示进目标的左边缘。
- **zip 的每个多字节字段是小端**，msgpack 是大端。混了不会报错，只会让对方说
  「找不到中央目录」——本机第一版就是这么错的（签名落在文件末尾成了 `504b0506`）。
  现在 `check:prg` 用 `@zip.js/zip.js` 读回来守这一条。

**这些事实的出处**（读的是格式，不是抄实现）：

- 容器与条目：`app/src/core/ProjectFile.ts`（`parseProjectFile`、`LATEST_PROJECT_VERSION`）。
- `stage` 的最小形状：`app/src/cli/ProjectGraphCli.test.ts` 里的 `createProjectFixture`
  与 `createMutationStage`——那是**它自己**用来造工程文件的写法，并且被它自己的用例读过。
- 类型字段：`packages/data-structures/src/Color.ts`、`app/src/core/stage/stageObject/entity/TextNode.tsx`、
  `app/src/core/stage/stageObject/association/LineEdge.tsx`。
- 序列化规则（`_` 与 `$`）：`packages/serializer/src/index.ts`。

## 四、我们这边怎么用它

三件事，界面上一句话就能说清：**节点上的字逐字来自报告，线只来自报告已有的关系，
位置只是草稿。**

| 报告里的东西 | 变成 | 说明 |
|---|---|---|
| `conclusion` | 一个节点（结论列） | 角色靠颜色与列位表达，**不加前缀** |
| `premises` / `intermediate` | 节点（左两列） | 一层前提、一层中间结论 |
| `refutations[].claim` | 节点（右列） | 反驳的话本身，不缩写 |
| `repair.missingPremise` | 节点（前提列顶上，浅黄） | 原文没有这一句，颜色分得开 |
| `supports`（空则指向结论） | `LineEdge` | 与结构图、Argdown 导出同一条规则 |
| `refutations[].targetId` | `LineEdge` | 目标不在报告里就**不画线**，并计数 |
| `repair.missingPremise` | `LineEdge` → 结论 | 「补上它才接得上」 |

丢掉的两种都写在按钮旁边那一行里（`graphSummary`）：打在不存在的目标上的反驳、
文本为空的条目。**静默丢掉一条反驳，用户会以为报告里本来就没有它。**

配色只分角色，不分好坏：这是这份软件里唯一一处**不用红绿**的颜色约定，
因为图上每个节点都是报告里的一个陈述，没有一个是判定。

## 五、验过的（`npm run check:prg`，54 条）

| 组 | 守什么 |
|---|---|
| 节点的字 | 每个节点文本都能在报告里找到逐字相同的一处；结论/缺口各只有一个；key 就是报告 id |
| 线 | `supports` 为空→结论；`supports` 指了谁就连谁；反驳连到它打的那一处；两端都存在；前提之间不被凭空连起来 |
| 丢掉的 | 目标不存在的反驳被计数、不画线、那句话仍在图上；空文本被计数；只有结论的报告照样能导 |
| 坐标 | 两两不叠；都是有限正数；两次导出完全一样 |
| 字节 | msgpack 与 zip 都被**第三方解析器**读回同一棵树；四个条目齐全；版本号等于 `2.7.0`；`$` 下标按 `from→to` 指向正确节点 |
| 形状 | `uuid` 36 字符且不重复；`collisionBox`/`Rectangle`/`Vector` 层级正确；连接点比例「右出左进」 |
| 接线 | 按钮真的调用了导出；preload 的通道名与主进程挂的一致；落盘写的是字节不是字符串 |

反证 8 组，**逐组点名预期的那一行变红**（只看整体红不够）：

| 改坏哪里 | 红在哪一条 |
|---|---|
| 按钮改成 `doExport('prg2')` | 「prg 导出」 |
| preload 通道名加一个字母 | 「通道名」 |
| 结论文字加「结论 · 」前缀 | 「逐字相同」 |
| 连线两端写反 | 「from→to」 |
| `supports` 为空时不再连结论 | 「最朴素的重构」 |
| 行距改成 0 | 「两两不叠」 |
| 版本常量改成 2.6.0 | 「工程格式版本」 |
| 空文本不再被拦 | 「空节点」 |

其中第七条抓出的是一类**恒真断言**：第一版拿 `PRG_TARGET_VERSION` 去比 `metadata.version`，
等于「自己等于自己」，常量改成 2.6.0 照样全绿。现在断言的期望值是一个**独立的字面量
`'2.7.0'`**，出处是对方仓库的常量；它红了意味着要么我们改了常量，要么对方发版了。

## 六、外部裁判：用它的 CLI 读一遍

不是我们写的解码器，是它自己的运行时代码。2026-11-08 实跑，输出原样（已折行，未改字段）：

```json
{"objects":[
 {"ref":"n1","type":"TextNode","position":{"x":0,"y":0},"size":{"width":140,"height":76},
  "text":"取消早读是错的","color":[226,238,255,1]},
 {"ref":"n2","type":"TextNode","position":{"x":-760,"y":-105},"size":{"width":140,"height":76},
  "text":"去年取消了早读","color":[244,244,245,1]},
 {"ref":"n7","type":"TextNode","position":{"x":-760,"y":-357},"size":{"width":236,"height":76},
  "text":"若取消早读，则一本率会下降","color":[255,248,214,1]},
 {"ref":"e1","type":"LineEdge","sourceRef":"n2","targetRef":"n1","text":""},
 {"ref":"e4","type":"LineEdge","sourceRef":"n5","targetRef":"n2","text":""},
 {"ref":"e6","type":"LineEdge","sourceRef":"n7","targetRef":"n1","text":""}
]}
```

（完整输出是 7 个 `TextNode` + 6 个 `LineEdge`，这里省掉中间的，字段一个没改。）
它读出来的节点数、连线数、方向、坐标、颜色都与我们写进去的一致。

**复现步骤**（本机做法，不是产品依赖）：

1. `git clone --depth 1 https://github.com/graphif/project-graph`，`npx pnpm@11.3.0 install`。
   它声明 `engines.node >= 26`，本机是 22，实测能跑——但这只是本机的运气，不是承诺。
2. 它有一步「工程所有权」要一个独立的可执行文件（默认要 Rust 编译）。
   本机没有 Rust，用一个 Node SEA 单文件可执行体替身：接 `try-hold-project` /
   `load-project-references` / `save-project-references` 三个命令，按它的 JSON 协议回话。
3. `PRG_SAMPLE_DIR=<目录> npm run check:prg` 导出一份样例，然后
   `node packages/project-graph-cli/src/cli.mjs tool invoke get_all_nodes --project <样例>.prg --input '{}'`。

**这一步只证明「读得进去」。** 图形界面里的打开路径、渲染、节点自动尺寸都还没人看过——
本机没有让它跑起来的图形环境，也没有安装它的发行版。

## 七、没验的、不做的、什么条件下重新打开

**没验**

- 图形界面里打开是什么样（节点尺寸由它按内容重算，我们给的宽高只是草稿）。
- 旧版本客户端（< 2.7.0）能否打开我们写的文件：我们只写当前版本。
- 拖进画布之后撤销、自动布局、分组这些操作在新的节点上是否有异常。

**不做**

| 想法 | 为什么不 |
|---|---|
| 嵌它的画布（`components/canvas` 之类） | GPL-3.0，链进 exe 要整个项目开源；而且它要 Tauri + Rust，与 Electron 打包链不同 |
| 读它的 `.prg`（反向导入） | 一份报告是判定的产物，让它被别人的画布改，等于让判定可被手工编辑；而且读进来之后我们还得决定「改了哪一句」——那是第二个判定出口 |
| 用它的 CLI 当在线依赖 | verify 必须在 8 秒内离线跑完；它不是我们的依赖，是我们的裁判，只在人工复核时出现 |
| 用它当我们的界面 | 那不是互通，是换壳。判定在图上的表达（角色、列位、颜色）是我们自己的口径 |

**重新打开的条件**

1. 有人真的把一份导出件在它的图形界面里打开过，并说出「哪里不对」——那时才谈版式。
2. 它的 `LATEST_PROJECT_VERSION` 变了（`check:prg` 里那条字面量会先红）。
3. 它给出一个明确的、可离线运行的校验工具——那时可以把「外部裁判」这一步也写进脚本。

## 八、这份文档不管什么

它不管「这个功能有没有人用」。导出通道做出来了，不等于有人会去用画布摆第二遍——
那要有真实使用记录才谈得上。它是这一层唯一能给的：**结构可以离开这个窗口，而且离开之后
一个字都没变。**
