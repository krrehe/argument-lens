# 长文本论证分析：专题研究

这份文档回答一个具体问题：**贴一整篇文章进来，这个工具到底发生了什么，哪些是它能负责的。**
它不列进度——完成了什么、还欠什么在 `docs/路线图.md` 的阶段状态里，那里是唯一一份进度记录。

---

## 一、结论先行

工具**早已能把长文干净地切开**，但切开与否的后果，此前从未被量化地摆出来。一次真实的长文本使用里，
软件既没有替用户切分（这是有意的设计），也没有告诉他「这份报告只碰到了原文的一小部分」——
于是最自然的那次输入，得到的是一份和短文本几乎一样厚的报告，而失败安静得看不出来。

这一层缺口是**可见性**，不是判定能力。补它不需要模型、不需要余额、不需要改提示词，也不需要改判定。

---

## 二、三层必须分开

「长文本优化」很容易被当成一件事，其实是三件，可信度与代价差着一整个量级：

| 层 | 问的是 | 谁来做 | 现状 |
|---|---|---|---|
| **切分** | 这一整篇里，哪几段各自像一条论证 | 本地纯文本启发式 | 已实现：`@shared/segment` + 切分条，给候选、标切点依据，**不替用户决定** |
| **覆盖** | 这份报告碰到了原文的哪几句、哪几段 | 本地逐字复算 | 本专题落的那一块：长文覆盖账 |
| **判定** | 长文里的论证站不站得住、该怎么分段问才对 | 模型 + 提示词 + 评测 | **没动**：要改提示词、要真模型评测（余额为空），且「怎么切才对」本身是人的判断 |

混淆这三层的典型错误：因为「报告太薄」就去改提示词，于是把覆盖问题当成判定问题，
用一次没有评测的改动去回答一个本来可以逐字复算的问题。

---

## 三、实测（本机存档，实时数跑 `npm run audit:longtext`）

2026-11-10 本机 104 份报告里，有 **1 份长文本**：6268 字、167 句、31 个自然段，
由 `deepseek-chat` 真模型跑出、存了模型原文；内容是关于彩礼与零彩礼的一段视频口播稿。
其余 102 份短文本平均 126.6 字，且高度集中在少数几段文字上——**它们不是随机对照组**。

| 指标 | 短文本基线（102 份） | 那份长文本 |
|---|---|---|
| 被报告条目落上的句子 | 396 / 502（78.9%） | **8 / 167（4.8%）** |
| 一句都没被落上的自然段 | 通常 0（只有 1 段） | **25 / 31（80.6%）** |
| 报告结构 | 平均 3.0 条前提 | 4 条前提、3 条检查、2 条反驳 |
| 切分条 | 不触发 | **触发，切出 31 段，全部按空行，0 处按字数硬切** |
| 模型自己的说明 | — | `scope.partialNote` 写着「大量篇幅是理论转述，本透镜不评」（界面有显示） |

两个读数要摆在一起：**文本长了约 49 倍，报告结构几乎没变**；而切分条其实工作得很好
（31 个切点全都有作者划的段界作依据），那次使用只是没有点它。

`scope.partialNote` 那句话界面确实显示了，所以「失败完全不可见」不准确。
准确的说法是：**只有模型的一句定性自述，没有任何一个本地可逐字复算的量**。
裸提示词也能写出那句话；「167 句只碰了 8 句、25 段没碰到」是只有本地工具才知道的事实。

数字口径与界面完全同源，不另算一份：句子与「有没有条目落上」取 `rereadOf` 的 quiet，
段落取 `segmentPassage` 的候选段，阈值取 `SEGMENT_HINT_CHARS`（800 字）。
换一台机器这些数会变；本命令依赖本机存档，**不进 `verify`**，没有长文本时明说量不了而不是假绿。

## 四、已有的长度上限（别重复发现）

长文本在这个仓库里不是新话题，动手前先把已有边界列全：

| 位置 | 上限 | 行为 |
|---|---|---|
| `src/main/analyze.ts` `MAX_LEN` | 15000 字 | 超过直接抛 `TOO_LONG`，文案是「请分段分析」 |
| `@shared/capture` `MAX_CAPTURE_CHARS` | 12000 字 | 剪贴板超长**不填、不截断**，明说字数与上限 |
| `@shared/rewrite` `REWRITE_MAX_CHARS` | 400 字 | 逐字比超过就明说「没比完」，不悄悄按前 400 字算 |
| `@shared/sideby` `SIDE_MAX_VALUE` | 400 字 | 两份对照的长值截断并标原长 |
| `@shared/agreement` `MAX_VALUE` | 110 字 | 同题复跑的长值截断并标原长 |
| `@shared/academic` `MAX_TRACES` | 14 条 | 待核线索最多 14 条 |
| 提示词库 | 不按文本动态裁剪 | 同一段文本、同一副透镜提示词逐字相同；最长一份约 15800 字符（保住指纹可比） |

这份 6268 字的文本没碰到前两道闸（< 12000 < 15000），所以**「被拦住」不是那次失败的原因**。
真正发生的是：整篇通过了范围门，模型把它压成了一条主论证。

`MAX_LEN` 那句「请分段分析」与切分条之间没有互相指向，是一处小的不一致；
但它只影响 >15000 字的输入，本机没有这样的真实样本，**这一轮不改**——没有证据的顺手优化，
正是这个项目一直在防的东西。

## 五、设计决定（写下来，别顺手优化掉）

1. **不替用户自动切分。** 切分条给候选、标依据、允许整篇直接分析；这个决定写在 `SegmentBar.tsx`
   的注释与 README，理由是「切分是启发式，切错必须看得出来，决定权在人」。覆盖账不推翻它：
   它只摆事实，不出现「建议切分」「应该分段」这类话。
2. **只在长文本上出现。** 短文本摆一条 100% 的账是空面板——不是「这一栏没内容」，
   是「这一栏根本不该渲染」。阈值直接用切分条的 800 字，不另写一个数。
3. **口径不另写一份。** 句子、`quiet`、段、阈值全部复用已有纯函数；覆盖账里「第 N 段」
   与「切给我看」里的第 N 段逐字是同一段，不重新切一遍。
4. **不判「漏了」。** 没被落上的句子可能是转述、铺垫、例子，本来就不该被分析；
   本地不知道，也不猜。不劝、不打分、不排优先级、不落盘、不改判定。
5. **不动提示词、不做分段汇总报告。** 分段跑完再合成一份总报告，听起来是「长文本分析」的正解，
   但它要回答「按什么切、切完怎么合、合并时谁说了算」——三个都是判定问题，
   且改提示词会让指纹变化、新旧报告不可比，验证要 `eval`（要钱、要 Key、余额为空）。
6. **不按长度裁剪提示词索引。** 指纹是同题复跑与重放的基准，动态裁剪会让它失去意义。

## 六、这一层做成之后，仍然没有回答的事

- **人看完会不会改行为**：零证据。本机真实用户 1 人，长文本报告 1 份，没有「下一句」记录。
- **真应用里的长文本报告长什么样**：端到端冒烟跑道用的是短文本示例，只验到「不该出现时整块不出现」；
  长文本那一版靠 `?coverage=1` 预览页（真组件渲染，但演示原文是仓库内示例拼接的构造文本）
  与静态断言守。**构造文本不是使用证据，也不能算 P2 输入。**
- **按什么切才对**：切分条只按空行、句末标点与少数连接词，它明确写着「这是切分，不是理解」。
  那 31 段全有依据，不等于那 31 段就是 31 条论证。
- **判定层值不值得走**：要一段使用者自己专业里的真文本（最好带一次真模型报告），
  或余额到位的跨模型评测；两件都不是再写一块本地计算能替代的。

`npm run audit:provenance` 量出的本地独立判定占比仍是 **4.8%**，本专题没有动它。
这一层改变的是「长文本上的失败第一次可见」，不是判定权，也不是「像 AI 加提示词」那条主线的进展。
