## 第 20 轮：「帮我规划一下」长期完善

用户要规划。先核事实再排路线——不看现状就排路线等于写愿望清单。

### 核出来的三个事实（其中两条修正了我原来的判断）

1. 87 份真实报告，**59 份带 `prompt` 版本**（2.4.0 + 指纹 c532993045d9）。我一开始看第一份没有就以为「字段从没被填过」——错了，是旧存档，设计上不回填假值。
2. **0 份保存模型原始输出。** 这是结构性缺口：报告是「解析 + 十道裁决」后的产物，那条链路会改模型的原始说法（改编号、合并结论、清引文、打回档位）。只存结果不存输入 → 永远无法回答「报告变了，是我改坏了，还是模型这次说的不一样」。两个变量同时动，不是实验。
   这也是**语义验证做不便宜的根因**：唯一验证方式是重跑六分钟十七万 token 的评测，而那次模型输出又变了。
3. 最新报告时间 13:29:45 —— 用户就在用。

### 规划（docs/路线图.md，新）

原则：**按「消灭哪个未知」排，不按「哪个功能大」排**。长期项目的死法通常不是功能不够，是力气花在已经知道答案的地方。

- P0 让验证变便宜（0 元）：P0-1 存原文 / P0-2 离线重放 / P0-3 一条命令跑完
- P1 语义质量的最小证据（小额）：语料扩到每陷阱两条 / 跨模型一致性 / 判定手册+独立标注
- P2 真实使用（只有用户能做）：10 段真实文本，只记「看完后的下一句话」
- P3 产品化（等 P2）

**不做清单**（长期项目最容易死在不断加东西上）：不加第七副透镜、不再加断言（已 800+，断言过剩会制造虚假安全感）、不做云同步账号（毁掉「本地+密钥自持」这个唯一硬优势）、不扩谬误名录、不做 Web/移动端。

**三条掉头条件**：P2 多数人的下一句是「所以呢」→ 形态该改（从报告改成陪改）；跨模型差异 >50% → 收缩承诺；半年内 P2 完不成 → 承认是个人工具，只修 bug。

## 第 21 轮：「开发新功能」

用户只说四个字，方向由我定：**报告带不走**。
理由：写作者真正改稿是在 Word / LaTeX 里，而处方层刚补上、却锁在应用窗口里。
「回应用看一眼」这个门槛足以让整条闭环断掉。带不走的报告，连被使用的机会都没有。

### 做了什么

**1. 导出为 Markdown**（`shared/report-markdown.ts` + `main/report-export.ts` + IPC + 按钮）
含：判定与限定、争议之点、结论与逐条引文、检查项（守着哪一处／依据／名称）、
倒在哪一关、**下一步的可勾选清单**（`- [ ]`）、缺的那句前提、反驳、命名与「这里没毛病」、
边界与可推翻条件、程序裁定（只 warn）。

三条自我约束（写在文件头）：
- 不替报告加自信（抬头第一句「这不是判决书」）
- 不留空壳（没内容的段整段不出现，空格子会被读成「没问题」）
- 不重算任何判定（只排版，处方与边界调原模块）

判了不适用的：导出短文件 + 说明「不适用不等于这段文字没问题」，**不出判定段**。

**2. 顺带显示了一个从未显示过的字段**：`whatIsRefuted`（只驳倒论证 vs 驳倒结论本身）。
算出来存了几个月，界面从没出现过。这两个对写作者意义完全不同：前者是没写够，后者是写错了。

**3. `shared/labels.ts`（新）**：把 ANSWER／BURDEN／STRATEGY／CONF／TAG／ACCEPT 六张标签表
从 Diagnosis.tsx 抽出来，界面与导出共用。同一枚举两处各写一遍，迟早说两套话。
（这个项目已经因为「两处各算一遍」吃过亏：明细与合计的金额口径。）

**4. CSS 变量检查**（补进 check-css-cover.mjs）
类名漏了整块裸奔、一眼看得出；**变量名写错只让那一条属性失效**，页面看着「还行」只是不对。
不报错、不崩溃、构建照过，和这个项目最忌讳的失败同形。
加上之后立刻抓到一处真缺陷：`styles-theory.css` 的 `var(--line-2, var(--line))`，`--line-2` 从未定义，
一直走 fallback。它看起来像「比 --line 再浅一档」，其实没有这一档。改成 `var(--line)`，视觉不变。
（第一版脚本把注释里提到的变量名也当成使用而误报，加了剥注释。）

### 从真实报告里看出来的三个问题（都修了）

导出后用真实报告（mvxedky1）通读一遍，读出三处：
1. `CQ2（CQ2 因果方向…）` —— label 已含编号又拼一次。修在 prescriptions 的 `nameOf()`。
   界线取「label 以 id 开头」，不是「包含 id」：「第 2 条 CQ2」这种正常写法不该被削掉。
2. `对方最可能的反击：对方可能答：……` —— steelman 自带引导语，又加一层标签，两个主语打架。
   自带引导语时让标签让位。
3. CQ2 与 CQ3 的「要填什么」**一模一样** —— 因为问法按「环」给、不按条给。
   一条时看不出，两条并排立刻变成「它是不是根本没看我的文本」。
   修法：同组内 need 重复时补上 guards 原文（「这一条针对的是：…」），不改「按环问」这个设计。
