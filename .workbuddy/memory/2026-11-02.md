## 第 27 轮：等的那一分钟（界面完善）

主题：**只在特定时刻出现的屏，没人见过**。这些屏不报错、不影响构建，代码读起来也像对的。

### 修了什么
- **分析进行中（30–90 秒）**：原来主区显示首屏空态「先给一段真话」——用户明明已经贴了文本、按了按钮。新增 `components/Running.tsx`：当前阶段名（主进程报的那句）、阶段换来的百分比（10/25/50/80/92，只在阶段切换时跳，不做匀速假进度）、「已等 42 秒」（本地数）、以及关窗的代价（请求已发出，供应商照收，本机账本记不下）。
- **按钮被撑裂**：`.primary` 的 loading 文案原先是整句阶段名，把按钮撑成三行，顺带把「128 字」「填入示例」各挤成两行。改为「分析中…」，整句交给主区面板；另给 `.composer .count/.ghost-btn` 加 nowrap + flex:0 0 auto。
- **设置页同一错误显示两遍**：`save()` 里同时写 `saveError`（正文小字）与 `test`（粉色条），相隔 40px。改为只写 `saveError` 并把 `test` 复位（避免「连上了」+「没保存」同屏自相矛盾）；`.hint.warn` 加左竖线、加深文字。
- **用量明细的「回」读成方块**：`sup.est` 8.5px 的汉字「回」在视觉上就是方框套方框，与缺字豆腐块无法区分。改两个字的「回填」（`.est-note`），「估」上标提到 10px；说明文案点名「标着回填的就是」。
- **滑块系统蓝**：`.field input[type=range]` 从未设样式，Chromium 默认蓝是整屏暖色纸面里唯一的高饱和色，而且就在首次启动那一屏。加 `accent-color: var(--accent)` 并去掉边框/底色。

### 新增截图入口（每屏都拍得到）
- 预览页：`?running=checking&wait=42`、`?dlg=settings[&onboard=1][&bad=1]`（bad 会自动替人按一次保存，让校验失败那一行进入画面）。

### 反证（红了才算）

### 教训

- 上一轮 `sup.est` 只用 title 说明含义不够：用户不悬停就不知道标记是什么，说明段里也没点名。
- `npm run build` 与 `npm run smoke` 不能并发：有一次 build 刚写完 out/ 就起应用，出现两条与改动无关的失败（模式横幅）。build 完成后再跑。

## 第 28 轮：给「长期只靠 AI 开发」装轨道

用户交代了长期打算：这软件要长期做，但代码只由 AI 写。这句话翻译成工程要求是——
**每个接手的会话都不带上次的记忆**，于是靠记忆维持的东西（口头约定、聊天里拍板的设计、
心里记着的待办）全部失效。要么写进仓库并有人守着，要么等于不存在。

### 做了什么

1. **`AGENTS.md`（新，138 行）** —— 交接书，不是产品文档。内容只保留「不看会做错」的部分：
   三十秒版、开工前三步、五条不可动摇、三条操作规矩、十五关一览（红了说明什么）、
   改什么要跑什么、会找错的目录、交付必说三件事、已决定不做的事。
   **它不写断言条数**——没有断言守着的数字一定会烂，实时数以命令输出为准。

2. **`scripts/check-docs.mjs`（新，`npm run check:docs`，第 15 关）** —— 守文档不腐烂：
   - 点名的 `npm run X` 必须在 `package.json` 里存在
   - 点名的 `src/` `docs/` `scripts/` 路径必须存在
   - `verify` 会跑的每一关必须写进 `AGENTS.md`（新增检查没写进交接书 → 红）
   - README 声明的「N 项」必须等于 `verify --list` 实算（为此给 `verify.mjs` 加了 `--list`，
     让算法只有一处，文档去核对代码）
   - 说「十一道裁决」，`analyze.ts` 里就必须正好 G1–G11
   - 交接书 ≤ 200 行（超过就没人读了，等于没有）
   共 26 项。

3. **路线图状态更新**：P0-3 补记 `check:docs` 与「文档也是会被改坏的东西」。

### 反证（红了才算）

- 临时插一个 `check:phantom` 脚本 → 红（「verify 会跑它，但 AGENTS.md 一个字没提」）。

  于是那条断言没红，看起来像「检查写漏了」。反证被抵消是安静的。

## 第 29 轮：判读从「一个结论」变成「一次示范」

用户要的是「不只是分析，还要教人知道为什么」。查下来最缺的不是说明文字（每栏都有一句人话），
而是**判读到检查项之间那一步是空的**：指针写着「在这里」，却没说凭什么在这儿、凭什么是这格不是隔壁。

### 做了什么

1. **`src/shared/verdict-trail.ts`（新，纯函数）**：点数（过/没过/没答）、找「钉住它的那一关」
   （认 `defeat.checkId`，退到「没过的」再退到「没答的」，都没有就说没有）、给出三格释义
   （只从 `theories.ts` 的 `levelMeaning` 取，界面不新立规则）、给「判不了」的排除理由
   （模式 → 范围 → 程序改档 → 兜底，顺序有讲究：把「查谬误本来不判」说成「信息不足」是把设计说成缺陷）。
2. **`VerdictWhy.tsx`（新）**：三步链（问了几关 → 钉住哪一关 → 所以落在哪格）+ 三格对照
   （当前格加描边与「本次」）+ 程序改档留痕（`CATALOG_OVERREACH` / `SCOPE_LEVEL_FORCED` / `MODE_NO_VERDICT`）。
   第三步不再单独写一行释义——那会和三格对照里的同一句重复，读者会以为是两件事。
3. **刻度尺**：`undetermined` 时撤掉原生刻度值与「伤到论证/结论」两个胶囊。留着它，
   同一行里会一边写「判不了」一边挂「CQ2 未答，属削弱性击败」。
4. **`mock-data.ts`**：CQ2 从 `violated` 改成 `unanswered`——同一份数据里三处文案都写着「CQ2 未答」，
   只显示文案时这个矛盾一直没露出来，把事实摆到说法旁边它一眼就是错的。
5. **端到端**：三个探针（`vwhy`/`vlad`/`vnow`）+ 一条双向断言：给档位的模式 ≥2 步、三格正好 3、**正好一格**标本次；
   不判的三个模式一处都不许有。
6. **`shot-ui.mjs`**：宽度可选（第 5 个参数）。报告栏跟着窗口变宽，截特写时放宽能少换几行。

### 反证（红了才算）

- 把渲染改成 `{false && …}` 重打 → `vwhy:0` 全红；恢复后回绿。
- 查谬误模式跑一趟，确认「不判的模式不出推导链」这条反向断言也是绿的。
- `?oos=1`（范围门判不适用）单独截图核对：判不了那一步、三格无一格标本次、胶囊只剩刻度名。

### 教训

- **量要量对阈值**：我拿 `<250` 当「有内容」，扫出内容一直到画布边缘，判成横向溢出；
  实际是 250 与 255 的差别（背景色 vs 白色面板）。阈值选错，量出来的结论比不量更误导。
- **说法与事实可以不一致，且只显示其中一样时永远发现不了。** 这次两处都是这么露出来的：
  假数据 CQ2、以及「判不了」旁边还挂着击败结论。
- **引用释义要按当前档取**：跨透镜对照那句我先写了 `pragma.levelMeaning.withstands`，
  句子却挂在「被削弱」名下——同一个词指着两个档，读的人不会发现，只有对着代码看才发现。
- 撤掉一个判定，就要把它派生的话一起撤掉；留一半比全留更糟。

## 第 28 轮：「停」——从界面一路 abort 到主进程 fetch

**需求**：用户按了分析之后 30–90 秒内除了关窗没有任何退路。关窗的代价是连界面一起没了，
而请求照样跑完、照样计费。（`abortRef` 以前只是个「丢掉迟到结果」的标记，从没真的停过任何东西。）

### 做法

1. **`analyze.ts`**：`runAnalysis` 的 opts 加 `signal`，一路传给 `chat()`（两次调用共用同一个）。
2. **`llm.ts`**：catch 里**先判 `opts.signal?.aborted` 再判 `AbortError`**——两者底层同源，
   但一个是你叫停的、一个是它太慢。混成一句，用户按「停」会读到「请求超时（120 秒）」。
   另加一处「接上监听之前就已 abort」的检查：`addEventListener` 不会补发已发生的事件，
   而格式修复的第二次调用正好落在两次调用之间那个缺口里。
3. **`index.ts`**：模块级 `Map<webContentsId, AbortController>`；`analysis:run` 建控制器、finally 里
   只删自己那一条（有新的顶上时删错就再也停不掉）；新增 `analysis:cancel`，返回 `{ok, canceled}`
   ——`canceled:false` 是真会发生的（请求刚好跑完），那种时候不能报「已停止」。
   窗口 `closed` 时 abort，否则关窗后请求最长跑到 120 秒，跑完还会 saveReport 写一份到历史里。
4. **`App.tsx`**：`stopping` / `stopRef` / `stopNote` 三个状态。三种结局各有说法：
   真停住（info 条，不是红条——红条写着「分析未完成」并配「看余额」，那是故障的样子）／
   没赶上（报告照给 + 一句「没赶上」）／停不下来（明说还在跑）。
   `waited < 1` 时说「还不到 1 秒」：`waited` 每 500ms 更新，刚按下时是 0，「等了 0 秒」读起来像坏掉的计数器。
5. **`Running.tsx`**：`停` 按钮 + 代价说明。按钮不用主色——这一屏的主行为是「等」。
6. **端到端**：`MOCK_DELAY_MS=3000 SMOKE_CANCEL=1`，14 条断言。关键一条是**从按下到面板消失的毫秒数**
   （<1.5 秒）。只验「面板消失」会被骗：abort 没接上时，面板会等模型回来再消失，看着也像停了。

### 自己抓到的错

- 文案先写的是「账本里不会留下这一条」，**假的**。`analyze.ts` 的 catch 会 `recordChatUsage({ok:false,
  estimated:true})` → 账本里有一条金额记 0 的失败记录，余额不扣。用户按文案去账本里翻会看到它。
  改成「会多一条失败记录（金额记 0）、余额不扣」，并把它写进 README 已知限制。
  「没记账」和「记了个 0」是两件事。

### 反证

- 拿掉 `analyze.ts` 里 `signal` 的传递 → **5 条红**（含「停是立刻生效的」「历史里没多出一份」）。
  有意思的是「请求真的停下了」仍然绿——面板在 3 秒后模型回来时才消失。
  所以时间上界不是锦上添花，它是唯一能分辨这两种结局的量。

### 没验

- 「没赶上」那条分支（abort 打在已完成的请求上）没法确定性复现，只有代码路径，没有断言。
- `dist` 两次遇到 electron-builder 的 ETIMEDOUT（拉 electron zip），重试才成。
